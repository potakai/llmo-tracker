# 抽出の評価

AI の回答から「自社・競合がどの順番で、どう書かれているか」を抜き出す抽出器が、どれくらい正しいかを数字で測る。
正解データ（ゴールデンセット）を抽出器に流して採点し、表で出す。

- ゴールデンセット：`eval/golden.json`
- 採点：`src/eval/score.ts`（純粋な関数）
- CLI：`src/cli/eval.ts`
- 結果の保存先：`eval/results/<YYYYMMDD-HHmm>-<extractor>.json`（git には入れない）

## 使い方

```bash
# ルールベース（費用ゼロ。CI やエージェントが流すのはこちらだけ）
pnpm --filter @llmo/llm eval -- --extractor rule

# 1件だけ流す
pnpm --filter @llmo/llm eval -- --extractor rule --only acct-prose

# LLM（本物の OpenAI API を叩くので費用がかかる）
pnpm --filter @llmo/llm eval -- --extractor llm --concurrency 4

# 保存済みの LLM の出力で、突き合わせだけをやり直す（API は呼ばないので費用ゼロ）
pnpm --filter @llmo/llm eval -- --extractor llm --replay packages/llm/eval/results/<file>-llm.json
```

| オプション              | 意味                                                                                        |
| ----------------------- | ------------------------------------------------------------------------------------------- |
| `--extractor rule\|llm` | 必須。`rule` は `createRuleBasedExtractor`、`llm` は `createLlmExtractor`                   |
| `--only <id>`           | そのケースだけ流す                                                                          |
| `--concurrency <n>`     | 同時に抽出する数（既定 4）                                                                  |
| `--replay <path>`       | `--extractor llm` のときだけ。保存した結果の LLM の生の出力を使い、API を呼ばずに採点し直す |

標準出力には、指標の表（Markdown。PR にそのまま貼れる）と、外れたケースの一覧（id・正解・抽出結果・どの判定が外れたか）が出る。
感情だけが外れたケースは、詳細を出さずに id だけを1行にまとめる。
全ケースの詳細（抽出器が返したもの、LLM の生の出力、かかった時間）は `eval/results/` の JSON に残る。

### LLM での評価は、手元で人が実行する

`--extractor llm` は本物の API を叩いて費用がかかるので、CI やコーディングエージェントは流さない（AGENTS.md のルール）。人が手元で、次を用意してから流す。

- ルートの `.env` に `OPENAI_API_KEY`（なければ分かりやすいエラーで止まる）
- モデルは `EXTRACTOR_MODEL`。なければ本番（`createExtractorFromEnv`）と同じ既定値（`DEFAULT_EXTRACTOR_MODEL`）

LLM のときは、使ったトークン数と推定費用（`estimateCostUsd`）も出る。まず `--only` で1件流して費用を確かめてから全件を流すとよい。

1件の抽出が失敗しても全体は止まらない。失敗したケースは不正解として数え、理由を一覧に出す。
LLM の抽出器は失敗するとルールベースに切り替えて結果を返すが、評価ではこれも**失敗**として数える（LLM の精度にルールベースの結果を混ぜないため）。

### 突き合わせだけを変えたとき（replay）

LLM の出力を、登録済みの名前と突き合わせる処理（`reconcile`）や感情の変換だけを変えたときは、`--replay` で前に流した結果ファイルを指定する。
結果ファイルの各ケースに残した LLM の生の出力（`result.raw`）に、現在のコードをかけ直して採点する。API は呼ばない。

- 入力はゴールデンセットの現在の内容を使う（結果ファイルの中の入力は使わない）
- 結果ファイルで失敗・フォールバックしていたケースは、replay でも失敗として数える
- 結果は `eval/results/<YYYYMMDD-HHmm>-llm-replay.json` に残る。これもまた replay できる
- プロンプトやスキーマの変更の効果は replay ではわからない（LLM の出力そのものが変わるため）。`--extractor llm` で流し直す

## 既知の制限

### ルールベースは、ひらがなの一般名詞を、カタカナで登録した会社と取り違える

`normalize` は、ひらがなとカタカナを同じとみなす（「そらはた会計」を「ソラハタ会計」として数えるため）。
そのため、ルールベースの抽出器は、本文のひらがなの一般名詞（「かんたん」）を、カタカナで登録した会社（「カンタン」）として拾ってしまう。
`acct-generic-word-competitor-hiragana` はこの取り違えを確かめるケースで、ルールベースでは外れる想定。

LLM の抽出器は、LLM が拾った名前だけを登録済みの名前と照らす（本文の文字列一致では足さない）ので、この取り違えは起きない。
ルールベースで一般名詞を見分けるのは、この評価の対象外としている。

### LLM は、出典の記事タイトルの中だけに出てくるブランド名を拾ってしまう

`acct-citation-title-only` は、本文では紹介されておらず、出典の欄の記事タイトル（「[1] 「電子帳簿保存法のポイント」ソラハタ会計 公式ブログ」）にだけブランド名が出てくるケースで、正解は「言及なし」。
プロンプトには「出典・参考文献の欄、記事タイトルの中だけに出てくる名前は抜き出さない」と書いてあるが、gpt-5.4-mini は手元で流した 4 回とも、このブランド名を返した（2026-11-21）。

突き合わせ（`reconcile`）は LLM が返した名前だけを使うので、LLM が返したものを後から消すことはできない。
本文と出典の欄を分けて LLM に渡すなど、プロンプトの外での対応が要る。それまでは、このケースは LLM の抽出器では外れる想定（評価の表では不正解として数える）。

## ケースの追加方法

`eval/golden.json` に1件ずつ足す。形は次のとおり。

```jsonc
{
  "id": "acct-prose", // 英小文字・数字・ハイフン。重複しないこと
  "note": "どのケースを確かめるためのものか",
  "input": {
    // ExtractInput と同じ形（abortSignal を除く）
    "answerText": "AI の回答文",
    "brand": { "name": "ソラハタ会計", "aliases": ["Sorahata Kaikei"] },
    "competitors": [{ "id": "kumotsumugi", "name": "クモツムギ会計", "aliases": ["Kumotsumugi"] }]
  },
  "expected": {
    "brandMentioned": true,
    "brandRank": 2, // mentions の中のブランドの位置（1始まり）。出てこなければ null
    "sentiment": "positive", // positive / neutral / negative。ブランドが出てこなければ null
    "mentions": [
      // 回答に出てくる順。同じ会社は最初の登場の1回だけ
      { "entityType": "competitor", "competitorId": "kumotsumugi", "name": "クモツムギ会計" },
      { "entityType": "brand", "competitorId": null, "name": "ソラハタ会計" },
      { "entityType": "unknown", "competitorId": null, "name": "ミドリカエデ帳簿" }
    ]
  }
}
```

- ブランド・競合は**架空の名前**にする（実在の会社名は使わない）
- `name` は回答の中の表記のまま書く（全角半角・大文字小文字の違いは照合のときにそろえる）
- `unknown` には、回答の中で紹介・推薦・比較されている、登録されていない会社・サービスを入れる。「会計ソフト」のような一般名詞は入れない
- 正解ラベルは PR で人がレビューする。判断が分かれそうなら `note` に、どう判断したかを書く

### ラベル付けの基準

正解ラベルは次の基準で付ける。迷うケースは、どちらに倒したかを `note` に書く。

**言及（mentions / brandMentioned）**

- 回答の本文に名前が出てくれば、推薦していなくても言及として数える。「今回の比較から外しました」「提供終了のため候補に入れていません」のような、推薦ではない言及も含める
- URL や出典（参考文献の記事タイトルなど）の中だけに出てくる名前は、言及から除く。引用元は別に計測しているため
- 名前に似ているだけの別のもの（「ミソラハタ会計」と「ソラハタ会計」、「ホシツグミ給与」と「ホシツグミ帳簿」など）は、登録済みの会社として数えない。会社・サービスとして紹介されていれば `unknown` にする
- 一般名詞（「会計ソフト」「クラウド会計」）や、競合の名前と同じ形の普通の言葉（「カンタンに確認できる」の「カンタン」）は数えない

**表記の違い**

- 全角・半角、大文字・小文字、カタカナ・英字、ひらがなの違いは、同じ会社として数える。登録済みの別名にない表記（「そらはた会計」など）でも、同じ会社だと読み取れれば数える
- 同じ会社が別の表記で何度も出てきても（「リンクモリア（LinkMoria）」など）、1社として数える
- `name` には、最初に出てきたときの表記をそのまま書く

**順位（brandRank / mentions の並び）**

- 回答の中で最初に出てきた位置で決める。導入文で先に名前が出れば、そのあとの番号付きリストで2位でも1位とする
- 未登録の会社（`unknown`）も順位に数える

**感情（sentiment）**

- 回答の本文でブランドがどう書かれているかだけで判断する。順位では判断しない（リストの1位でも短所だけなら negative、最下位でも長所だけなら positive）
- positive：長所だけが書かれている、または推薦している
- negative：短所だけが書かれている、または勧めない・他社を選ぶよう促している。「避けたほうが無難」のようなはっきりした否定も、「以前は定番でした」「今から導入するなら他社のほうが後悔は少ない」のような遠回しな否定も含める
- neutral：長所と短所の両方が書かれている、事実（料金・機能）を並べているだけ、または比較から外したことだけが書かれている
- ブランドが出てこなければ `null`

読み込むときに zod で検証する。`brandRank` と `mentions` の位置が合わない、`competitorId` が `input.competitors` にない、同じ会社が2回ある、などはエラーになる。
`pnpm test` でも、スキーマに合うこと・id が重複しないこと・正解の表記が回答文の中にあることを確かめる。

## 指標の定義

| 指標                                     | 定義                                                                                                                                                                  |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 全問正解のケース                         | 未登録の会社以外の判定（下の表の上から6つ。感情を採点しない抽出器では感情を除く）がすべて正解だったケースの割合                                                       |
| ブランド言及の正解率                     | `brandMentioned` が一致した割合                                                                                                                                       |
| ブランド順位の正解率                     | `brandRank` が完全に一致した割合（`null` 同士も一致として数える）                                                                                                     |
| 感情の正解率                             | 正解でブランドが言及されているケースを分母に、`sentiment` が一致した割合。抽出器が `null` を返したケースや失敗したケースは不正解                                      |
| 登録済みの会社の適合率 / 再現率 / F1     | brand と competitor を対象に、`competitorId` で照合する（表記は問わない）。全ケースの TP / FP / FN を合計してから計算する（マイクロ平均）。F1 = 2TP / (2TP + FP + FN) |
| 登録済みの会社の順序一致率               | 正解と抽出結果の両方に出てくる登録済みの会社だけを取り出し、その並び順が完全に一致した割合。共通の会社が2つ以上あるケースだけが対象                                   |
| 未登録の会社（unknown）の適合率 / 再現率 | `normalize()` した名前で照合する。表記の揺れに弱いので参考値                                                                                                          |

- 順位（`brandRank`）は、未登録の会社も含めた登場順で数える。ルールベースは未登録の会社を拾えないので、ブランドより前に未登録の会社があると順位がずれる
- 抽出に失敗したケースは、すべての判定を不正解として数える（順序は、正解に登録済みの会社が2つ以上あるときだけ不正解に数える）
- 分母が0の指標は `—`（null）と表示する
- F1 は 1つも当たらなければ（TP = 0）0% になる。null（`—`）になるのは、正解にも抽出結果にも登録済みの会社がない（分母が 0）ときだけ
- 感情を採点するかは、評価結果ではなく抽出器の仕様で決める
  - `--extractor rule`：ルールベースは感情を返さない仕様なので、採点しない。感情の正解率は 0% ではなく対象外（`—`。結果の JSON では `null`）にし、各ケースの感情の判定も対象外（`null`）にして、全問正解の判定からも外す。表の下に「全問正解の判定に感情を含めていない」と注記が出る
  - `--extractor llm`：LLM は感情を返す仕様なので、採点する。`null` を返したケースや抽出に失敗したケースも分母に入れ、不正解として数える
